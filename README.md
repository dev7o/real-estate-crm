# عقاري — نظام متابعة مبيعات العقارات

نظام متكامل مبني بـ **Next.js 15** لإدارة رحلة العميل العقاري الكاملة: من الاستفسار الأول، مرورًا بالمعاينة الميدانية والتفاوض، وصولًا إلى الحجز والتعاقد ومتابعة خطة السداد — مبني وفق وثيقة متطلبات المنتج (PRD) المرفقة.

---

## 🧱 المكدس التقني (Tech Stack)

| الطبقة | التقنية | السبب |
|---|---|---|
| الواجهة | Next.js 15 (App Router) + React 19 | Server Components + Server Actions تقلل الكود وتُبسّط الربط بقاعدة البيانات |
| اللغة | TypeScript (strict mode) | أمان الأنواع عبر كامل المشروع |
| التصميم | Tailwind CSS 3 + نظام تصميم مخصص | هوية بصرية عقارية احترافية، بلوحة ألوان مستقلة لكل قسم |
| قاعدة البيانات | SQLite + Prisma ORM | حسب الطلب — محلية، بدون إعداد خادم منفصل |
| الرسوم البيانية | Recharts | تقارير وتحليلات لحظية |
| الأيقونات | Lucide React | مجموعة أيقونات نظيفة وخفيفة |
| التحقق | Zod | يتحقق من صحة كل نموذج قبل وصوله لقاعدة البيانات |

## 📁 هيكلة المشروع

```
src/
├── app/
│   ├── (dashboard)/              ← كل الأقسام خلف الشريط الجانبي المشترك
│   │   ├── dashboard/            ← لوحة التحكم الرئيسية
│   │   ├── leads/                ← العملاء المحتملون (CRM)
│   │   ├── projects/             ← المشاريع والمخزون العقاري
│   │   ├── pipeline/             ← خط أنابيب المبيعات (Kanban)
│   │   ├── site-visits/          ← المعاينات الميدانية
│   │   ├── reservations/         ← الحجوزات المبدئية
│   │   ├── contracts/            ← العقود الموقّعة
│   │   ├── payments/             ← خطط السداد والتحصيل
│   │   ├── reports/              ← التقارير والتحليلات
│   │   └── settings/             ← المستخدمون والصلاحيات
│   └── layout.tsx                ← إعداد RTL + الخطوط العربية
├── components/
│   ├── ui/                       ← عناصر تصميم أساسية مشتركة (Button, Card, Badge...)
│   ├── layout/                   ← الشريط الجانبي وشريط الأدوات العلوي
│   └── <module>/                 ← مكوّنات كل قسم في مجلده الخاص (مطابق لطلب الفصل بين الأقسام)
├── lib/
│   ├── actions/                  ← Server Actions — منطق العمل الفعلي لكل نطاق
│   ├── validations/              ← مخططات Zod لكل نموذج
│   ├── db.ts                     ← Prisma Client (Singleton)
│   ├── constants.ts              ← تسميات وألوان الحالات بالعربية
│   └── utils.ts                  ← دوال تنسيق مشتركة (عملة، تاريخ، أرقام)
prisma/
├── schema.prisma                 ← نموذج البيانات الكامل (يطابق قسم 9 في PRD)
└── seed.ts                       ← بيانات تجريبية واقعية لتجربة النظام فورًا
```

**كل قسم مستقل في مجلده الخاص** (`components/leads`, `components/projects`, ...) وله **هوية لونية خاصة به** معرّفة في `tailwind.config.ts` تحت `colors.module.*` — هذا يحقق الفصل التصميمي المطلوب بين الأقسام مع الحفاظ على مظلة بصرية موحّدة.

## 🚀 التشغيل على جهازك

> ⚠️ **ملاحظة مهمة:** هذا المشروع تم بناؤه بالكامل في بيئة بدون اتصال إنترنت، لذا لم يُشغَّل أو يُختبر فعليًا هنا. الكود جاهز ومكتمل، لكن نفّذ الخطوات التالية على جهازك للتأكد من عمله وإصلاح أي خطأ بسيط قد يظهر (نادر لكن وارد).

### المتطلبات
- Node.js 20 أو أحدث

### الخطوات

```bash
# 1. تثبيت الحزم
npm install

# 2. إنشاء قاعدة البيانات المحلية وتطبيق النموذج
npm run db:push

# 3. تعبئة بيانات تجريبية واقعية (مشاريع، عملاء، صفقات، عقود...)
npm run db:seed

# 4. تشغيل النظام
npm run dev
```

افتح `http://localhost:3000` — سيتم توجيهك تلقائيًا للوحة التحكم.

### أوامر إضافية مفيدة
```bash
npm run db:studio   # واجهة رسومية لتصفح قاعدة البيانات مباشرة
npm run build        # بناء نسخة الإنتاج
```

## ⚠️ حدود يجب معرفتها قبل الإطلاق الفعلي للعميل

بصفتي بنيت هذا بأمانة كاملة، إليك ما لم يُنفَّذ بعد ويحتاج عملًا إضافيًا قبل تسليم المشروع فعليًا لشركة عقارية:

1. **لا يوجد نظام مصادقة (Login) فعلي بعد** — الشاشات الحالية تفترض مستخدمًا واحدًا (سارة العتيبي) بدون تسجيل دخول حقيقي أو فصل صلاحيات مُطبَّق فعليًا على مستوى الاستعلامات. يوصى بإضافة **NextAuth.js** وربط كل استعلام بصلاحية المستخدم الفعلية.
2. **SQLite مناسب للتجربة والمرحلة الأولى فقط** — عند وجود عدة مستخدمين متزامنين فعليًا في الإنتاج، يُنصح بالترحيل إلى PostgreSQL (تغيير سطر واحد في `schema.prisma` + إعادة `db push`).
3. **لا يوجد رفع ملفات فعلي** (صور الوحدات، مستندات العقود) — الحقول موجودة في قاعدة البيانات (`imageUrl`, `documentUrl`) لكن تحتاج ربطًا بخدمة تخزين (مثل S3 أو Cloudinary).
4. **الإشعارات داخل النظام والبريد الإلكتروني غير مُفعّلة فعليًا** — البنية جاهزة (حالات الأقساط، انتهاء صلاحية الحجز) لكن الإرسال الفعلي يحتاج تكاملًا مع خدمة بريد (Resend/SendGrid) أو Cron حقيقي.

كل ما سبق **نقاط توسّع محدّدة بوضوح وليست عيوبًا في الأساس المعماري** — الأساس (قاعدة البيانات، منطق منع الازدواج، الهيكلة) مبني ليتحمّل إضافتها لاحقًا دون إعادة هيكلة كبرى.
